# Project Context

Last updated: 2026-10-14. This file is a short handoff index, not the full product specification. Detailed decisions and unresolved proposals are linked below.

## Product

- Menuki (Mi Plan Saludable) is an online app with personal data isolated per Supabase account and a shared recipe-proposal inbox for authenticated users. It is published as a static GitHub Pages site from the `dev` branch.
- The current interface is Spanish. It plans three weeks with five meal slots per day (105 planned meals per cycle), tracks recipes, shopping, pantry stock, completed activity sessions, and weight.
- Supabase Auth and the HTML login are configured for email/password without email confirmation. The repository has transactional relational sync to thirteen existing RLS-protected personal-state tables. Seven initial migrations are applied through SQL Editor. The eighth migration, `20261013120000_menuki_sync_conflict_http_409.sql`, is prepared but not yet applied. The owner reports that the ninth migration, `20261013160000_recipe_proposal_inbox.sql`, has been applied and the admin assignment query has been run. It creates a private admin allowlist plus normalized proposal, ingredient, and step tables, with scoped `submit_recipe_proposal`, `is_menuki_admin`, and admin-only `clear_recipe_proposals` RPCs. The project owner assigns admin membership after the account exists; no role is inferred from browser credentials. The first access imports local v8 state once. Later devices read Supabase and the client checks `sync_revision` every 15 seconds while visible, on focus, and on reconnection. Stale writes are automatically rebased against a local common base; Supabase's latest accepted revision wins same-value conflicts. `localStorage` remains a working copy, not cross-device storage. There is no offline queue. A confirmed full reset replaces the account's rows transactionally and is separate from normal sync. Credentials stay in `auth.users`, not `public.profiles`. Snapshots have indefinite retention while the parent completion and account exist; no timed purge is configured. Monitor total and per-table database size as users are added, reviewing around 350 MB of the 500 MB Free quota. The owner reported 27 MB database size on 2026-10-13. SQL Editor does not track repository migration history.
- The owner reports migration 10, `20261013170000_recipe_proposal_admin_maintenance.sql`, is applied and individual proposal deletion works. Bulk purge failed with PostgreSQL error `21000: DELETE requires a WHERE clause`; migration 11, `20261013180000_recipe_proposal_purge_where_clause.sql`, adds `WHERE id IS NOT NULL` to the protected purge RPC and remains to be applied.
- Inicio gives the first viewport to its banner, KPIs, and today's nutrition progress, sized to the available width and height. Scrolling reveals «Menú de hoy» and the meals for the current date; week/day navigation remains on Menú. Its day card puts the date number, weekday, and activity button on the first line, with the session status below and no “objetivo base” label when there are no sessions. First-use guidance lives in Guía and directs the user to review generic profile values; saving persists `profile_confirmed` locally and remotely. Future meals are labeled planned and cannot be completed before their date. Published browser flows and two-user RLS validation are still pending.
- Supabase sync runs automatically after changes while online. The compact account status offers retry only after a sync error. Personal-state JSON export and restore/import controls, plus periodic backup reminders, are not part of the interface. Existing local browser state keeps its v5-v8 migration path. Admins have a separate, versioned JSON download for recipe proposals, defined by `docs/schemas/recipe-proposal-export.schema.json`.
- On mobile, the bottom navigation shows Inicio, Menú, Compra, and **Más**. Despensa, Recetas, Proponer receta, and admin-only Revisar propuestas are under **Más**; Perfil, Aprende a usar Menuki, Actividad y peso, and sign-out are in a dropdown on the sticky branded toolbar. The account email remains in Perfil and sync error/retry stays in the toolbar. Mobile Inicio uses weekly meal-completion and current-streak KPIs plus a daily calorie ring and macro progress bars fed only by completed meals; desktop KPIs remain unchanged. ## Catalogs and planning

- Generic food and recipe catalogs are stored in `data/foods.json` and `data/recipes.json`, version `0.8.0`: 90 foods, 112 recipes, and 543 ingredient references. This release adds Ensalada templada de gulas and five foods for it; the gulas nutrition reference now uses the manufacturer's natural product label. Version 0.7.0 added two foods and four reviewed recipes from the first proposal export; the bone-in wing nutrition estimate combines USDA FoodData Central with USDA Food Buying Guide edible yield. Recipes have no food-photo metadata; the app keeps only brand imagery. Bone-recovery tags qualitatively mark selected calcium, vitamin D, and vitamin C food sources; these are not nutrient amounts or clinical targets. When recovery is active, new or regenerated proposals favor recipes with these sources and show ingredient presence across the 21 days. The active cycle is not replaced automatically. Whole fruit and vegetables are weighed in recipe grams and tracked in pantry/purchases as units; nutrition and portions use the recipe measure. Eggs remain units and liquids use millilitres. Their contracts are in `data/foods.schema.json` and `data/recipes.schema.json`.
- The HTML loads both JSON catalogs over HTTP(S), checks IDs, units, ingredient references, and meal types, and maps them into the existing runtime model. The fixed `WEEK_1`–`WEEK_3` menu remains the initial cycle.
- `menuki.html` is the page shell. It loads `assets/css/app.css`, a pinned `@supabase/supabase-js@2.117.3` CDN build, and the `js/main.js` ES-module entry; the stylesheet groups base, shell, shared controls and views, with responsive rules at the end. JavaScript templates have no inline `style` attributes; progress indicators use `<progress>`. Food photos were removed; the brand logo remains. Dates are resolved against `Europe/Madrid`, while civil-day arithmetic uses `YYYY-MM-DD` dates carried at UTC midnight. Date/catalog/unit/local-state/Supabase transport modules and the shared HTML encoding helper have been extracted; UI and remaining orchestration still live in `js/main.js`. `npm test` runs the Node 20+ domain/catalog/HTML checks. Published browser flows and two-account RLS isolation remain to be validated.
- `data/foods.json` and `data/recipes.json` are the canonical generic catalogs. Supabase relational tables are canonical for personal data; `localStorage` is only the browser working copy. Runtime catalog models are derived from JSON, and the fixed initial menu remains a template of recipe IDs. Duplicate food/recipe/weight/pack literals have been removed from `js/main.js`.
- The user can generate a 105-meal proposal for the next cycle, review and swap recipes within the same meal type, lock selections, regenerate unlocked meals, and save the proposal in Supabase through the relational sync. The proposal records its catalog version and activates when its start date arrives. Stock is a soft preference; there is no minimum count of unused recipes, taste filter, or allergy filter.
- Recipe submissions are raw ideas, not catalog entries: authenticated users submit type, name, free-text ingredients, and ordered steps. Amounts and nutrition are intentionally omitted. Admins can edit or delete one proposal through admin-only RPCs, then download a privacy-minimized, versioned JSON package and use a repository-connected Codex chat to enrich the remaining proposals. The owner reports that migration `20261013170000_recipe_proposal_admin_maintenance.sql` is applied and individual deletion works. Bulk purge needs migration `20261013180000_recipe_proposal_purge_where_clause.sql` after Supabase rejected `DELETE` without a WHERE clause.
- Four initial planning principles are accepted. Exact scoring thresholds, dislike handling, and multi-person preference aggregation are not decided. See the planner specification and open questions.
- Activity sessions are entered after they happen. Net estimated energy `(MET - 1) × weight_kg × duration_hours` affects only uncompleted meals on that date. Completed quantities stay fixed; the remaining daily target is distributed across the meals still pending, primarily through carbohydrates. Future dates use the base goal; history does not automatically learn or alter a routine. The manual-activity-summary idea remains open. See decision ADR-0005.
- Selecting a start date with an archived cycle reactivates its existing cycle ID and menu. Menuki reverses its unreversed meal completions through compensating pantry movements, retains the completion and reversal history, and opens the meals as pending again. See ADR-0027.

## Data and safety rules

- Keep public generic catalogs separate from personal profiles and activity data. Raw recipe ideas live in the private Supabase proposal inbox until manual AI-assisted catalog work is published.
- State format v5 is the oldest local browser state migrated; the current state format is v8. Keep v5-v8 local-state migration and do not support v1-v4 or personal JSON restore. Migration converts old recipe usage snapshots while preserving stock movements in their historical inventory units.
- `food.unit` is the pantry/purchase unit and `food.recipeUnit` is the recipe unit. Whole produce uses recipe `g` and pantry/purchase `ud`; eggs use `ud`, solids are weighed in `g`, and liquids use `ml`. Milk is purchased in 1 L cartons.
- If a logged meal consumes more than recorded stock, record the full consumption and show the deficit. Reversals must not be applied twice.
- Legacy strength-day flags may remain in existing local state but are inert; fixed-menu third-amount overrides were removed. Activity sessions, weights, pantry movements, menu cycles, and shopping selections sync to their corresponding tables.
- ADR-0008 accepts immutable per-ingredient completion snapshots in recipe units, separate from inventory movements, with indefinite retention and no scheduled purge. Track database size as users are added; review near 350 MB. ADR-0009 accepts email + password, open registration, and no email confirmation. ADR-0010 records relational sync and its one-time import. Two-user RLS isolation and published PC/mobile flow remain unverified.
- No offline queue. The UI must only report a successful remote save after Supabase confirms it; on failure it keeps the local working copy and shows pending/error status. Ordinary cross-device changes reconcile automatically; confirmed full reset remains a separate operation.
